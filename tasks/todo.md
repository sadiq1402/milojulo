# Media links (#35) ‖ Profile setup (#38), in parallel

Founder choices (2026-10-14): build these next; image library react-native-image-crop-picker (pick, crop locked to 4:5, compress). Scope: profile photos only; chat media links come with #12 ‖ #45, R2 cleanup on account deletion with #20. R2 signing is hand-rolled AWS SigV4 with Web Crypto (no new dependency). Contract:

- Edge Function `media` (POST, JSON, `Authorization: Bearer <user JWT>`; signed-out → 401 `{ error: 'sign in first' }`; other refusals 400/403/404 `{ error: '<message>' }`):
  - `{ action: 'photo-upload', position: 1..4, contentType: 'image/jpeg', size: bytes }` → `{ photoId, uploadUrl, expiresIn }`. JPEG only, size ≤ 5 MB (`photo must be a JPEG of at most 5 MB`). The app PUTs the file to `uploadUrl` (headers `Content-Type: image/jpeg` and `Content-Length` = the declared `size`, both signed, so R2 refuses anything else) within `expiresIn` seconds (300). The link points at a staging key (`uploads/<member id>/<photo id>.jpg`), never at a live photo.
  - `{ action: 'photo-confirm', photoId }` → `{ ok: true }` after checking the staged object in R2 is within the limits and copying it server side to the live key; the photo then takes `position`, replacing any photo already there (old object deleted from R2, unless an admin took it down: that file is kept as evidence). Refusals: `no photo upload to confirm`, `the photo didn't arrive; try again`.
  - `{ action: 'photo-delete', photoId }` → `{ ok: true }`: deletes the caller's own photo (the profile minimum still applies: `add at least 2 photos`, 400) and then its R2 file (best effort; kept for a photo an admin took down). Refusal for not-mine or unknown: `no photo to delete` (404).
  - `{ action: 'photo-urls', photoIds: uuid[] (≤ 60) }` → `{ urls: { [photoId]: string }, expiresIn }` (signed GET, 600 s). Ids the caller may not see are left out, never an error, so a Block is never revealed. R2 keys never leave the function.
- Who may see a photo (SQL, security definer, service role only, tested in pgTAP): the owner (any confirmed, unremoved photo); otherwise confirmed photos that aren't hidden or removed, of a Member who is not blocked either way, not banned, deleted or Auto-hidden, and whom the caller may see in Discover/profile view or shares a Connection, Join Request or Activity with. Pending (unconfirmed) photos: owner only, and only as upload state.
- Function code: thin handler over injected dependencies (database client, R2 client, clock) so the rules are unit-tested with Deno and the database rules in pgTAP; secrets `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` from the function environment (local: `supabase/functions/.env`, gitignored).
- App data module `src/features/photos/api.ts` (#38 builds it against this contract): `uploadPhoto(position, localUri): Promise<string>` (photo-upload → PUT → photo-confirm, returns the photo id), `deletePhoto(photoId)` (calls the `photo-delete` action, so the file goes too; direct deletes under RLS still work but leave the file), `movePhoto(photoId, position)` (calls `move_photo(photo_id, new_position)`, which swaps with whichever photo holds the position; refusals `no photo to move`, `choose a photo position from 1 to 4`), `fetchMyPhotos()`, `fetchPhotoUrls(ids): Promise<Record<string, string>>` (batched, ≤ 60 per call). Refusal messages map to friendly copy.
- Profile setup (#38): five steps per the mockups Setup1Basics to Setup5Interests, saving as you go, ending in `submit_profile()` and landing on Discover; photos picked and cropped to 4:5 at 1080 x 1350, JPEG quality 0.8.
- Shared local Supabase: never `db reset`; integration tests through `flock /tmp/milojulo-integration.lock`.

# Join Requests (#14) ‖ Join screens (#47), in parallel

Contract both sides build against (messages are the database's exact text; the app maps them to copy):

- Table `activity_requests` (`id`, `activity_id`, `requester_id`, `status request_status`, `created_at`, `responded_at`, `withdrawn_at`; unique (activity_id, requester_id)); requester and host select under RLS, no direct writes. `connections.activity_id` (nullable, FK on delete set null). One Join Request per Member per Activity: a cancelled, withdrawn or declined one can't be asked again.
- `join_activity_request(activity_id uuid) returns uuid` (the request id). Refusals, in this order: `unpause your profile to join activities`, `your profile is not visible`, `no activity to join` (not on the caller's board: unseen, blocked, cancelled, over), `you cannot join your own activity`, `this activity has already started`, `you already asked to join this activity`, `no spots left`, `you have sent 10 join requests in the last 24 hours` (Join Cap, every request created in a rolling 24 h counts, cancelled ones too).
- `respond_activity_request(request_id uuid, accept boolean) returns uuid`: host only, request `requested`, Activity open and not started, pair not blocked, requester not banned, deleted or Auto-hidden; else `no join request to answer`. Accept refuses `no spots left` when full. Accept returns the Activity Connection id: the pair's accepted Connection (Mode unchanged), or their pending Connection Request accepted as it stands, or a new accepted Connection (`requester_id` joiner, `addressee_id` host, Mode `activities`, `activity_id` set). Decline returns null.
- `withdraw_activity_request(request_id uuid) returns void`: requester only, before `starts_at`; `requested` → `cancelled`, `accepted` → `withdrawn` (`withdrawn_at`), the Activity Connection stays; else `no join request to withdraw`.
- `get_activity` gains `my_request_id uuid`, `my_request_status request_status`, `connection_id uuid` (the caller's Connection with the host when their request is accepted; null otherwise). `venue_detail` goes to the host and accepted joiners. An accepted joiner keeps reading the Activity while it's open and not over.
- `activity_join_requests(activity_id uuid)` (host only, else empty) returns `request_id, requester_id, requester_name, requester_photo_id, requester_area_id, status, created_at, connection_id`: requested and accepted ones, oldest first, without blocked (either way), banned, deleted or Auto-hidden requesters.
- `my_join_requests()` returns `request_id, activity_id, activity_title, activity_starts_at, other_id, other_name, other_photo_id, direction connection_direction, created_at`: pending requests on open Activities not yet started, `incoming` (to my Activities; other = requester) and `outgoing` (mine; other = host), same exclusions, newest first.
- `activity_spots_left` = capacity − accepted; `activity_is_locked` = any accepted. `update_activity` on a Locked Activity refuses title, time, end, Area or venue changes and any lower Spots (even down to the accepted count) with `this activity is locked: only its description and a higher number of spots can change`.
- `block_user` also cancels pending and withdraws accepted Join Requests between the pair, either way round.

Until #14 merges the app hand-adds these to `database.types.ts`; regenerate after merging.
