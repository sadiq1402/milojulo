# Architecture

```
RN CLI app ───────────────► Supabase (Mumbai)
   │  direct, under RLS        ├─ Postgres: RLS, PostGIS, pg_cron
   │  + function calls         ├─ Postgres functions (business rules)  ◄── your code
   │                           ├─ Edge Functions (TypeScript)          ◄── your code
   │                           ├─ Realtime (Broadcast, private channels)
   │                           └─ Auth (email OTP, JWT)
   │
   ├── signed URLs ──────────► Cloudflare R2 (photos, chat media)
   └── (admin page, web, later) ► Supabase, admin role claim

Edge Functions ──► FCM (HTTP v1), Google Places API (New)    Auth ──► Resend (SMTP)
```

## Two paths
1. Simple reads and writes (own profile, chat) go straight to Supabase under RLS.
2. Anything privileged is a Postgres function: discovery feed and scoring, connection requests, accept, block, report, age gate and consents (which create the profile), circle join, meetup feedback, account deletion, and the admin actions (`admin_takedown`, `admin_restore`, `admin_ban`, `admin_create_circle`, `admin_edit_circle`, `admin_archive_circle`).
Edge Functions only do what SQL cannot, and there are six: `media` (signs R2 upload and download links and checks uploaded files), `push` (sends through FCM), `account-purge` and `purge-chat-media` (delete R2 files), `copy-evidence` (copies reported media to the `evidence/` prefix, #160, decision 62) and `places` (searches Google Places for an Activity's venue, #248, decision 70). The database calls `push`, `account-purge`, `purge-chat-media` and `copy-evidence` over HTTP with `pg_net`; the app calls `media` and `places`.

## Components
- **Auth**: Supabase Auth, email OTP (6-digit code valid 1 hour, not magic link; template `supabase/templates/code.html`). The hosted project sends through Resend over SMTP (`smtp.resend.com`, from `no-reply@milojulo.co.in`), set under `[remotes.cloud]` in `supabase/config.toml` and applied with `supabase config push`; the sending domain needs SPF, DKIM and DMARC. Rate limits on the hosted project: one code per address every 30 s (the app's resend wait) and 30 emails an hour. Not built yet: Cloudflare Turnstile (#70) and the disposable-email blocklist (#71). Self-declared date of birth, 18+ (checked in `accept_consents()`). Label it "email verified" only; the real "Verified" badge is reserved for a later selfie/phone check.
- **Database**: Postgres in Mumbai with PostGIS. Location is one offset point per Member in `member_locations` (moved 200 to 500 m in a fixed random direction, latest only, readable by no client; decision 40); a Member with no point from the last 30 days is not a Discover candidate and sees an empty feed (decision 66). Matching is SQL (`discover_feed`): candidates are Visible, unblocked Members within the viewer's Discover Range, with no waiting or accepted Connection between them; every Mode is shown (decision 45). Score: shared tags, shared availability, shared Modes and nearness; the Networking filter ranks by shared industry and career stage first. Distances are shown as bands (`<2 km`, `~N km`).
- **Chat**: client inserts a message with a client-generated UUID; RLS checks participant, accepted connection, no block. Delivery uses Broadcast from database triggers on one private channel per Member (`member:<id>`, decision 51), with RLS on `realtime.messages`; the app joins it once while signed in. Do not use Postgres Changes for chat: it authorises every event per subscriber on a single thread and does not scale with compute. The same channel carries live updates for read state and Media Consent, taken-down messages, Mode Change proposals and outcomes, Connection Requests and Join Requests. After a reconnect or a return to the foreground, fetch messages newer than the last seen and refetch what is on screen. Read receipts: one `last_read_at` per participant. A message an admin takes down is announced to both sides (`message-removed`, ids only), and an open chat drops it at once (#163). Not built: typing indicators and presence.
- **Media (R2)**: private bucket. Upload: app asks an Edge Function for a short-lived upload link (checks user, file type, size). New photos are live once the upload is confirmed (no pre-approval, decision 15); admins take down reported ones. Download: link issued only after the same visibility and block checks. Profile photos (#35, decision 28) go through the `media` Edge Function: `photo-upload` makes an upload slot and returns a presigned PUT to a staging key `uploads/<member id>/<photo id>.jpg` (JPEG, at most 5 MB, valid 300 s, Content-Type and Content-Length signed, so R2 refuses another type or size); the app PUTs straight to R2; `photo-confirm` checks the staged file with a signed HEAD, copies it server side (S3 CopyObject) to the live key and deletes the staged file, then the photo takes its position (the photo it replaces is deleted from R2, unless an admin took it down: kept as evidence). Upload links never point at a live key, so a still-valid link can't overwrite a live photo. `photo-delete` deletes the Member's own photo through SQL (the profile minimum applies) and then its file; `photo-urls` takes up to 60 photo ids per call (a whole feed page) and returns presigned GETs valid 600 s, leaving out ids the caller may not see. Object keys are `<member id>/<photo id>.jpg`; the app only ever handles photo ids and signed links. R2 requests are signed with a small hand-rolled AWS SigV4 (Web Crypto), no SDK. Chat media (#12) works the same way: `chat-upload` (`connectionId`, `kind` image/video/voice, `contentType`, `size`; image JPEG ≤ 5 MB, video MP4 ≤ 20 MB, voice M4A ≤ 5 MB, the fixed maximums) makes a slot through `start_chat_upload()` (accepted, unblocked Connection; an image within the settings row's limit; the sender's daily media allowance not used up, decision 60; in a Casual Connection images and video need both sides' Media Consent) and returns its `uploadId` and a presigned PUT to the staging key `uploads/chat/<connection id>/<upload id>.<ext>` (valid 300 s, Content-Type and Content-Length signed); after the PUT, `chat-confirm` checks the staged file with a signed HEAD against the slot's type and size, copies it server side to the live key `chat/<connection id>/<upload id>.<ext>`, deletes the staged file and confirms the slot, returning the `mediaKey`. The app then inserts the message with that key, which the database accepts once, from that sender, for that Connection, kind and type. Chat upload links never point at a live key either, so a still-valid link can't overwrite sent media. `chat-urls` takes up to 60 message ids and returns presigned GETs valid 600 s for the media messages the caller may open (their Connections, no Block, not removed, not expired; in a Casual Connection, images and video only while both sides have Media Consent on, decision 33). Staged uploads that are never confirmed are removed by an R2 lifecycle rule on the `uploads/` prefix (delete after 1 day), set by the founder in the Cloudflare dashboard (supabase/README.md); the function also deletes the staged file of a slot it discards. The function runs with `verify_jwt = false` so it can answer `sign in first` itself; signed-out calls therefore still reach the function and count as invocations before it refuses them. Store `object key + provider` in Postgres so media can move later. Compress images on the phone. Chat media limits come from one settings row, `chat_media_settings`, read through `chat_media_limits()` (decision 59; launch values video 15 s, image 2 MB, voice 2 min, one media message per sender per Connection per 24 h (decision 60); never above the fixed maximums video 30 s and 20 MB, image 5 MB, voice 2 min and 5 MB); chat media deleted after 90 days.
- **Places (venue search)**: the `places` Edge Function holds the Google key (`GOOGLE_PLACES_KEY`) and calls Places API (New). `autocomplete` (`input`, `sessionToken`) returns `suggestions` of `{placeId, mainText, secondaryText, matches}`, biased within 50 km of the caller's fresh Member Location (read server side through `place_search_bias()`, rounded, never returned); `details` (`placeId`, `sessionToken`) returns `{placeId, name, address, lat, lng}` with the field mask `id,displayName,formattedAddress,location`. One session token per search, so Google bills the typing and the pick as one session. Signed-out callers get `sign in first` (`verify_jwt = false`, like `media`); Google failures answer 502 `place search is unavailable; try again`. The app then sends the place to `post_activity()` / `update_activity()`.
- **Push**: FCM only. The app registers a device token (`@react-native-firebase/messaging`, `register_device_token()`). Database triggers queue a row in `push_queue` (new Connection Request, request accepted, message, Join Request, join accepted, meet nudge), honouring the Member's `notify_messages` / `notify_activities` settings and mutes; a trigger on `push_queue` calls the `push` Edge Function over `pg_net`, which sends through the FCM HTTP v1 API (service-account OAuth), drops dead tokens and deletes the row; a push FCM couldn't take for now (429, 5xx), or one never handed over, stays queued and the `retry-queued-pushes` job sends it again, up to an hour after it was queued (decision 57). No Expo push service.
- **Mobile app**: React Native CLI (bare) in TypeScript. Supabase JS client with an async-storage session and URL polyfill. TanStack Query keeps an allowlist of lists and catalogs on the phone between launches (decision 52). `react-native-keyboard-controller` keeps bottom sheets above the keyboard on Android, where edge-to-edge windows and Modals don't resize (decision 58). The chat screen blocks screenshots and screen recording on Android through a small in-repo native module (FLAG_SECURE, no dependency); iOS does nothing. iOS builds need macOS.
- **Scheduling**: `pg_cron` runs six jobs: `expire-activities` (every 15 minutes, SQL), `send-meet-nudges` (daily 05:30 UTC, SQL), `retry-queued-pushes` (every 5 minutes: sends again any push still queued after a minute and drops ones an hour old), `account-purge` (hourly at :15), `purge-chat-media` (daily 21:30 UTC) and `copy-report-evidence` (every 15 minutes, for evidence copies a report's own call didn't get through). pg_cron schedules SQL only; the three jobs that need R2 call their Edge Function over HTTP with the `pg_net` extension, using the project URL and service role key stored in Vault (supabase/README.md).
- **Admin**: Supabase dashboard for now; the Next.js moderation page (`apps/admin`) is not built. Admins are users whose JWT carries `app_metadata.role = 'admin'` (`is_admin()`). Takedown, restore, ban and the Circle admin functions (create, edit, archive) write to `admin_actions`, which is append-only.

## Limits to design around
- Edge Functions: 2 s CPU per request (async I/O not counted), 256 MB memory, 150 s wall clock on free, 20 MB bundle, outgoing ports 25/587 blocked. Free plan includes 500,000 invocations a month.
- Realtime: Free 200 concurrent connections / 100 msgs per second; Pro with spend cap 500 / 500; Pro without cap and Team 10,000 / 2,500. Adjustable via support. Each foreground user holds one connection.
- Supabase free: 500 MB database, projects pause after about a week of inactivity, no daily backups. Upgrade to Pro before the beta.
- Cloudflare R2 free tier: 10 GB storage, 1M Class A and 10M Class B operations a month, free egress. Cloudflare may require a payment method before the first bucket. Set a billing alert.

## Scaling path (in order)
1. Indexes (a spatial index for the distance check) and connection pooling.
2. Chat on Broadcast from the start (this is the fix that matters).
3. Raise the Realtime plan limits before a few hundred are online at once.
4. Precompute candidates per user, cache the feed, then a read replica for discovery.
5. Only then consider moving hot paths to a container service. Business rules stay in SQL so they move with Postgres.
Load test with k6 before the beta (several hundred chatters plus feed loads) and watch slow queries.

## Environments and delivery
Supabase CLI for migrations and functions. GitHub Actions, all on pull requests only (`main` is protected and a branch must be up to date to merge, so a run on `main` would only repeat the pull request's): `db-tests` (every migration and pgTAP test on a fresh database), `function-tests` (Deno fmt, lint, check and tests per function), and the app's lint, typecheck, unit and integration tests. A deploy to the hosted project runs on every backend change to `main` and can be run by hand (supabase/README.md); the Android release build to Firebase App Distribution is run by hand only, to keep inside the account's Actions minutes. Supabase logs. Crash reporting (Sentry) is not set up. Schema and infrastructure live in git.
