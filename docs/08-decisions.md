# Decision log

Format: decision, why, alternatives rejected. Update this file whenever a decision changes.

1. **Auth: Supabase Auth with email OTP only (phone later).** Cognito does not come from Supabase and complicates RLS. SMS OTP in India needs DLT registration and costs per message, so it waits for beta funding. Phone attaches to an existing account later.
2. **Backend: Supabase only, with Postgres functions plus a few TypeScript Edge Functions.** One platform, one bill, one deploy tool, free until the beta. Rejected: AWS Lambda with FastAPI (free but needs an AWS account with free-plan expiry rules and extra setup; Python was preferred for build speed); Google Cloud Run (free tier appears limited to US regions, which is far from a Mumbai database); Cloudflare Python Workers (new, 10 ms CPU on free, WebAssembly package limits); Firebase (Cloud Functions and Storage need the pay-as-you-go plan, Firestore is a poor fit for relational, geo and block-aware matching).
3. **Business rules in SQL.** Keeps the language of the thin API layer almost irrelevant, scales with Postgres, and is portable to any Postgres host.
4. **Chat transport: Realtime Broadcast from database triggers** on private channels with RLS on realtime.messages. Postgres Changes was the first sketch but does not scale (single-threaded per-subscriber authorisation). (Built; since decision 51 one private `member:<id>` topic per Member.)
5. **Media on Cloudflare R2** (founder decision) instead of Supabase Storage: 10 GB free, free egress (video in chat), cheap beyond. Costs: second vendor, payment method may be required, access control must be rebuilt as signed URLs from an Edge Function, delete R2 objects on account deletion. Store object key plus provider so it can move.
6. **Matching: rule-based SQL, no LLM in V1.** Cuts cost and complexity; AI becomes one more signal later.
7. **Moderation: invite-only plus manual approval of profiles and photos** for the first few hundred users. *Superseded by 15.*
8. **Android first** (Google Play closed test doubles as the beta); iOS after the Apple fee is paid.
9. **Scope expansion (founder decision):** Dating, Serious, Casual, Networking, Circles and media in chat were added to V1. Risk flagged: timeline is now a floor; Casual and media raise moderation and store-review exposure; build each mode behind a switch and open in stages if time is short.
10. **Colour: Orchid pop** (founder decision after research on women's colour preferences and competitor palettes). First scheme (rosewood and ochre on beige) was dropped for looking institutional.
11. **Logo: not final.** Overlapping-circles mark rejected (Mastercard resemblance). Leading candidate Mingle plus Tail wordmark; trademark search pending. (Superseded by 32.)
12. **UI standards:** 48 hit targets, 4-pt grid, pill controls, soft-shadow cards (see docs/05-ui-standards.md).
13. **Business idea:** the founder chose to focus on MiloJulo only. Revenue is postponed until retention is proven; likelier paths are ticketed events and venue partnerships before premium subscriptions.
14. **Mobile: React Native CLI (bare workflow), no Expo** (founder decision; the assistant had recommended Expo with development builds).
    - Why: full control of the native projects (Gradle/Xcode), no dependence on Expo's tooling or build service, free local Android builds.
    - Accepted costs: hand-maintained native config and React Native upgrades (use the Upgrade Helper), manual autolinking and native-module setup, FCM set up directly (no Expo push API), iOS builds require macOS (a Mac or macOS CI) because local iOS builds are impossible on Linux, no built-in over-the-air updates.
    - Bootstrap: `npx @react-native-community/cli@latest init` (the old `npx react-native init` is deprecated; projects must declare `@react-native-community/cli` as an explicit devDependency).
    - Escape hatch if it becomes painful: `npx install-expo-modules@latest` adds Expo modules to a bare app without a rewrite.
    - Consequences for other decisions: push is FCM only; Android-first beta (decision 8) fits because iOS needs a Mac or CI.
15. **No pre-approval of profiles or photos (founder decision, 2026-10-07; supersedes 7).** Members go live on profile submission; moderation is after the fact via reports (24-hour target), bans, word filter and invite codes (removed by 27). Accepted risk: nothing screens photos before others see them, which weakens the store-review answer for UGC with Casual mode; automated photo screening is the fallback. See docs/adr/0002-no-pre-approval-of-profiles-or-photos.md.
16. **Connections carry a Mode and are per-pair history rows** (one active per pair, consent-based Mode Change, accepted Join Requests create an Activity Connection). See docs/adr/0001-connections-are-per-pair-history-with-a-mode.md.
17. **Chat media limits and retention (2026-10-07).** Report-only moderation; video up to 30 s and 20 MB, voice notes up to 2 min; chat media deleted from R2 90 days after sending (message stays, shows "media expired"); media in reported messages copied to evidence and kept for the safety-retention period set by the lawyer. Casual Connections require Media Consent from both sides before images or video. (Amended by 55: nothing is copied; a report holds the original R2 key, which the purges skip.) (Video limit replaced by 59: chat media limits come from a settings row, launch video 15 s.)
18. **First name is part of the profile minimum (2026-10-09).** A profile cannot be submitted, or later edited, without a first name, alongside the photos, prompts, Mode and Area; submission also requires the age gate and consents to have been passed. Photo upload confirmation is service-role only, because only the upload Edge Function can check that the object exists in R2.
19. **Chat history after a Block, ban or Auto-hide (founder decision, 2026-10-12).** A Block closes the pair's Connection, and the closed Connection stays in both Members' history with the same details as an ordinary close, so the blocked Member can't tell they were blocked. Photo links for a blocked pair are still refused by the media-links function (#35, hard rule 9). A banned or Auto-hidden Member stays in other Members' history by first name, but without a cover photo until an admin restores them. (No unban exists yet, decision 56, so only an Auto-hidden Member can be restored.)
20. **Chat UI values (2026-10-12).** docs/05 already set the bubble (radius 22, 6 on the tail corner, 16/22 text) and the composer; tokens now carry them, plus composer padding 10 12 (from the Chat mockup) and a 10 orchid unread dot (from the Chats mockup). The first-meet safety note sits at the start of every chat's history rather than only in new chats, so in practice it's seen when a chat is new or short.

Chips can carry a Mode tint (`Chip tint`), as in the Discover and Send Request mockups, keeping Mode colours to tags and chips (docs/06). (The 30 s poll is gone: since #147 Connection Requests reach the Inbox live on the Member channel, decision 51, 20261101090000_live_inbox.sql.)

The profile uses the standard top bar (back, menu) instead of the mockup's back button floating over the photo, keeping 48 targets clear of photo content. Until signed photo URLs exist (#35), feed cards and the profile hero show a photo-tone placeholder with the initial. (Photo links built in #35, decision 28; cards and profile now show real photos.)
23. **Activity Board visibility and edges (2026-10-13).** The board hides Activities whose host is Auto-hidden (after Reports), banned or deleted; a Paused host's Activities stay, since pausing only hides you from Discover. Deleting an Activity (for example with its host's account) deletes Activity-card messages that point at it rather than leaving broken cards. Until the expiry job runs (every 15 min) the host can still edit or cancel an Activity whose time has passed; the board already hides it. Once an end time is set it can be changed but not cleared. The Locked Activity rules arrive with Join Requests (#14), the first way an Activity can lock.
24. **Activity Board screens (2026-10-13).**
    - The board is one list with Tonight, This weekend and Later headings rather than the mockup's segmented control, so nothing is hidden behind an empty tab.
    - Cards are tinted by Activity type (`activityTones`: the photo tones plus the Networking tint), as in the mockup; the type shows as a plain tag, not a Mode colour.
    - Date and time without a date-picker dependency: day chips (Today, Tomorrow, then the next five weekdays), a start-time Stepper in 30-minute steps and a length Stepper (30 minutes to 12 hours, or no set end). Everything is in India time whatever the phone's zone. The Stepper is a new shared component (docs/05).
    - Editing can't change the type (`update_activity` has no type) or remove a set end (null keeps it). A Locked Activity's form shows only the details and Spots (which can only go up), with a note saying why.
25. **Join Requests (2026-10-13).** One Join Request per Member per Activity: once declined, cancelled or withdrawn it can't be asked again. Accepting a Join Request when the pair already has a waiting Connection Request accepts that request as it stands (its Mode and note), rather than making a second Connection; an existing accepted Connection is reused with its Mode. A Block cancels waiting and withdraws accepted Join Requests between the pair, either way round. Joining, answering and withdrawing all stop once the Activity has started, and the host can't answer a banned, deleted or Auto-hidden requester (the same Members the host's list leaves out). An accepted joiner keeps reading the Activity and its venue until it ends, even while Paused or after an Auto-hide. Activity Connections don't count towards the Request Cap, since nobody sent them.
26. **Join Request screens (2026-10-13).**
    - Accepting a Join Request from the Inbox opens the chat with the joiner, as accepting a Connection Request does; accepting on the Activity itself keeps the host there (several may be waiting) and moves the joiner to a Going list with Open chat.
    - Cancel request and Withdraw both ask first and say the Member can't ask to join that Activity again (one Join Request per Member per Activity); a declined, cancelled or withdrawn request leaves a short note instead of the button.
    - "Ask to join" (the mockup says "Request to join"), so the button doesn't read like a Connection Request. A full Activity shows "No spots left" instead of the button.
    - The phone's clock decides only what to offer once an Activity has started or isn't open (no Ask to join, Cancel or Withdraw for the joiner, no Accept or Decline for the host); the database enforces the start itself. A request still waiting at the start says the host didn't answer it in time, and an accepted joiner whose chat was closed is told so instead of seeing Open chat.
    - Incoming Join Requests sit with Connection Requests under "Waiting for you" and count towards the Inbox badge; the caller's own waiting ones are listed under "Sent" and open their Activity. Join Requests aren't broadcast, so the list and badge poll every 30 s, like Connection Requests (decision 21). (The poll is gone: since #147 Join Requests arrive live on the Member channel, decision 51.)
27. **Open sign-up, invite codes removed (founder decision, 2026-10-13).** Anyone who signs in with an email can become a Member: the 18+ age gate and consents are the way in, and `accept_consents()` creates the profile row. `check_invite`, `redeem_invite`, `invite_codes` and `invite_redemptions` are dropped, and the app's flow is Welcome, Email, code, Date of birth and consents, profile setup. Why: lower friction for the beta. Accepted costs: no trust layer and no cluster control from codes (offline events and outreach now do that), and bot protection depends on Cloudflare Turnstile (#70) and a disposable-email blocklist (#71), neither built yet. The Reviewer Account still exists for store review, seeded with its date of birth and consents. Supersedes the invite-code parts of docs/01 and decision 15.
28. **Profile photo links (#35, 2026-10-14).** Pending uploads live in their own table (`photo_uploads`), not as unconfirmed `photos` rows, so a replacement can upload while the old photo at that position stays live, and an unconfirmed upload is never anyone's photo. Confirming inserts the new photo before deleting the old one, so replacing a photo of a Submitted Profile with only 2 never trips the minimum; the replaced file is deleted from R2. One slot per position (a new one replaces the earlier); slots older than an hour can't be confirmed and are discarded (with their files) when the Member's next slot is made. Who may get a photo link: the owner (confirmed, not taken down; hidden included); anyone else only live photos of a Member who is not banned, deleted or Auto-hidden, with no Block either way, and whom they may see in Discover or the profile view, or who shares with them a Connection (any status but declined: a waiting Connection Request counts both ways, so each side sees who is asking or being asked, and closed history keeps its faces), a waiting or accepted Join Request, or a place among the same Activity's accepted joiners ("shares an Activity" read as fellow joiners; host and joiner are covered by the Join Request). Join Request access persists after the Activity is cancelled or over, as history, like a closed Connection. Upload links point at a staging key (`uploads/<member id>/<photo id>.jpg`) with Content-Type and Content-Length signed; on confirm the function checks the staged file, copies it server side to the live key and deletes the staged one, so an upload link that is still valid can never overwrite a live photo. Unconfirmed staged files are removed by an R2 lifecycle rule on `uploads/` (1 day), set by the founder. A photo an admin took down keeps its file when the Member replaces or deletes it (evidence). Members delete photos through the function's `photo-delete` (`delete_photo()`, which keeps the profile minimum) so the file goes too; direct deletes under RLS remain for now and leave the file. A banned or deleted viewer gets only their own photos. Extra refusals beyond the contract: `accept the terms first` (no profile yet), `your account cannot add photos` (banned or deleted), `choose a photo position from 1 to 4`, `no photo to delete` (404), `add at least 2 photos` (400, from the minimum), `ask for at most 60 photos at a time`, `photoIds must be a list of photo ids`, `send a JSON body`, `unknown action`, `use POST`. A presigned URL necessarily carries the object path, so the key (`<member id>/<photo id>.jpg`, both already known to the app) is visible inside the link; it is useless without the signature. Signing is hand-rolled SigV4 with Web Crypto, tested against AWS's published examples; the function runs with `verify_jwt = false` and checks the caller itself so a signed-out request gets `sign in first` (such calls still cost an invocation). (Direct photo deletes refused since #168; only `photo-delete` deletes.)
29. **Profile setup screens (2026-10-14).**
    - Five steps in the mockups' order (Basics, Photos, Prompts, Modes, Interests); each step saves when the Member leaves it, by Next or by Back (the top bar's or Android's), so nothing typed is lost; Back saves without the step's minimum (blank prompt answers are left out, since an empty prompt would count toward the minimum) and a failed save keeps the Member on the step with the reason. Photos save as they upload. A returning Member resumes at the first step whose minimum isn't met. Interests and availability are optional, so the last step is always reachable. Step 1 has no Back (consents are done) and offers Sign out instead.
    - A refusal from `submit_profile()` opens the step that fixes it with the reason on that step, until the Member changes something there; success goes straight to Discover.
    - Photos: four 4:5 slots, the first is the main photo; only photos neither hidden nor taken down fill a slot, as in the profile minimum. Tapping a photo offers Make main photo, Move earlier, Move later, Replace and Remove; moving swaps with the photo there in one `move_photo` call, and removing closes the gap so the next photo becomes the main one. While a photo uploads, the other photos can't be moved or removed and the step can't be left (Android's back says to wait). Upload progress is a spinner, since the upload is a plain `fetch` PUT; a failed upload keeps Retry and Cancel on its slot and its reason above Next, which fits at 130% text. The mockup's "a person reviews every photo" note is replaced by a tip about the main photo (decision 15).
    - Prompts use the catalog's first two active questions (only two exist); with fewer than two the step says prompts aren't available instead of saving. A question picker waits for a longer catalog.
    - Modes are option cards; Casual carries an "18+ · adults only" tag. Choosing a Dating Mode shows own gender, genders to meet, an age range starting at the Member's age ±5 (18 to 99) and a maximum distance starting at 15 km (5 to 50 in steps of 5); these defaults are saved only while a Dating Mode is held. Networking shows optional profession, Industry and Career Stage.
30. **Circles (#15, 2026-10-14).** Circles are admin-created only: `admin_create_circle`, `admin_edit_circle` and `admin_archive_circle` are guarded by `is_admin()` and are not called by the app (seed and dashboard only). Members reach Circles through `browse_circles()` (active Circles for a visible Member, joined first then by name, each row carrying `member_count` and `i_am_member`), `get_circle()` (one Circle: active ones for a visible Member, plus the caller's own Circles and admins, so a member or admin still sees an archived Circle), `circle_members_of()` (fellow members only to a visible member of that Circle, excluding the caller, the non-visible and either-way blocks), `circle_activities()` (a Circle's upcoming Activities for a visible caller) and `join_circle()` / `leave_circle()`. Neither `circles` nor `circle_members` is readable or writable directly. Joining is idempotent and needs a visible profile and an active Circle (`your profile is not visible`, `no circle to join`); leaving refuses when the caller is not a member (`you are not in this circle`) and leaves the Member's posted Activities untouched. `post_activity` gained a trailing `circle_id`: posting to a Circle requires membership of that active Circle (`join the circle to post to it`). `activity_board()` and `get_activity()` gained `circle_id` and `circle_name`; `circle_name` (and `circle_activities`'/the board's label) is NULL once the Circle is archived (`is_active = false`), so an archived Circle drops its label while its Activities stay. A paused fellow member is treated as non-visible and so is left out of the member list, matching the contract's "excludes non-visible"; and a paused caller gets an empty member list, since `circle_members_of` requires the caller be visible too, like the other member-facing Circle functions. `created_by` on `circles` has no foreign key, so an admin without a profile row can still create one.
31. **Circle screens (#48, 2026-10-14).**
    - The Circles tab lists active Circles from `browse_circles()` (joined first, then by name, as the function orders them), each card showing the Circle's Area, its one interest (a tag) and a member count, with a "Joined" tag on ones the Member belongs to. A Paused Member sees the shared `PausedNotice` instead (Circles, like Discover and the board, come back empty while Paused), and an empty list says there are no Circles in the beta yet.
    - The Circle detail shows the Area and interest, description and member count; a non-member gets a single "Join Circle" button, and a member gets the fellow-members list, upcoming Activities (reusing `ActivityCard`), a "Post an activity to this circle" button and a confirmed "Leave Circle".
    - `circle_members_of()` leaves the caller out (`p.id <> auth.uid()`): "fellow members" are the *other* people in the Circle, the ones you can open and send a request to, so the members list never shows yourself and a Circle where you're alone says "No one else is here yet. You're the first." This was a contract ambiguity (the plan listed the columns but not whether the caller is included); resolved in favour of the database's implementation, which is the sensible reading for a list whose only action is to send someone a request. A short note under the list reminds the Member that chat opens one to one once the other side accepts.
    - Posting from a Circle opens the shared Activity form with the Circle pre-selected (a new `CreateActivity` route param) and a banner naming it; the Activity still shows on the main board. `activity_board()` and `get_activity()` now return `circle_name`, so a Circle-posted Activity carries a Circle label on its board card and detail; the label is dropped (the name comes back null) when the Circle is archived, while the Activity itself stays. Archived Circles disappear from the browse list and detail (a non-member who opens a stale link gets "This Circle isn't available any more").

33. **Casual Media Consent and chat media (#12, founder decisions, 2026-10-15).** Media Consent gates seeing as well as sending: while either side has it off in a Casual Connection, `chat-urls` gives no links to images or video in that chat, including ones already sent; voice notes and non-Casual Connections are unaffected. A Mode change into Casual switches both sides' Media Consent off, so consent given under another Mode never carries over (changing out of Casual leaves the switches as they were). Chat uploads go through a staging key and a confirm step like profile photos (decision 28), so an upload link never points at sent media.
34. **Chat media native libraries and screenshots (founder, 2026-10-15).** Native modules for #45: react-native-image-crop-picker (already used for profile photos) for camera and gallery photos and video, with JPEG compression on the phone; react-native-video for playback; react-native-nitro-sound for voice notes (record and play, AAC in M4A); react-native-compressor for video compression to MP4 at most 20 MB. react-native-nitro-modules comes with the last two as their required peer. The secure-screen flag is a tiny in-repo Android module (FLAG_SECURE) set on chat screens, with no dependency. No other native additions. Screenshots: Android blocks them in chat screens; iOS does nothing, and the app never claims screenshots are blocked there; Safety Centre copy may say screenshots are blocked on Android only. Media Consent (from #12): in a Casual Connection, image and video links are withheld while either switch is off, and moving a Connection into Casual resets both switches to off.
35. **Learning loop (#19, founder decisions, 2026-10-15).** Only Activities that ran ask for feedback: status `open` past its end, or `expired`; cancelled and removed Activities are refused and never appear in the pending list. A Kept Connection counts each pair of people once, whichever route (an Activity or chat) and however many times; `kept_connections` dates it from the earliest route on which both said they met and want to keep it. `submit_meetup_feedback(other_user, did_meet, keep, activity default null)`: both answers required. Feedback about a banned, deleted or Auto-hidden Member is refused, as the pending list leaves them out.

The app sends them to the consent step to accept again or delete their account.

39. **Requests under the other Member's Mode (#101, founder, 2026-10-15).** A Connection Request can be sent under one of the other Member's Modes; accepting adds that Mode to the Connection. Casual only when both chose it. Built in #104 and #107.
40. **Exact coordinates, reversing hard rule 7 (#101, #102, founder, 2026-10-15).** The phone's location is stored in `member_locations`: latest point only, no history, moved by a fixed random offset of 200 to 500 m per Member, readable by no client role (owner and admins included) and used only inside security definer functions; deleted with the account. Pinpointing defences: the offset, rounded distance bands on cards ("<2 km", "~3 km"), location set from the device only, at most one accepted update an hour, and points outside the Pune box (18.40 to 18.75 N, 73.65 to 74.05 E) refused as implausible jumps. A Member with no location (permission denied) is measured from their Area's centre. The app refreshes on open, foreground only, at most every few hours; no background location. Native module: `@react-native-community/geolocation`. See docs/adr/0003-member-location.md. (The Pune box became a row in `service_regions` in decision 42; the app sends a point at most every 3 hours.)
41. **Discover range and the data notice (#102, founder, 2026-10-15).** `profiles.discover_range_km`: 2, 5, 10, 25 or 50 km, or null for anywhere in Pune; default 10; one-way (limits only what the Member sees). The data notice gains location, so it moves to v2: a Member who has not accepted every current document (missing or withdrawn) is hidden as in decision 37 and `needs_reconsent()` tells the app to send them to Reconsent. Existing Members, the Reviewer Account included (rerun `seed_reviewer`), accept v2 before they are visible again.
42. **Discover feed rules and Service Regions (#103, founder, 2026-10-17).** `discover_feed` shows a Member when both are Visible, no Block stands, they are inside the viewer's Discover Range (null: anywhere in the viewer's Service Region) and the viewer has at least one of their Modes to see. A Member who chose Casual (even beside other Modes) is shown only to Members who also chose Casual (amended by decisions 44 and 45). A Dating Mode (Dating, Serious, Casual) is seen only when both sides' Dating Preferences fit and the other Member's own Discover Range includes the viewer; a Member whose only Modes are Dating Modes is therefore absent otherwise. The Modes filter keeps Members who chose that Mode (and, for a Dating Mode, pass the checks above). Score: shared tags + shared availability + shared Modes + nearness (3 under 2 km, 2 under 5 km, 1 up to 10 km); the Networking filter still ranks by shared Industry and Career Stage first. Cards and profiles show a band (`<2 km`, `~N km`, rounded to the kilometre) and the other Member's visible Modes. A Member Location older than 7 days is ignored (Area centre instead). The Pune box moved into `service_regions` (a new city is a row); `set_location` refuses a point outside every active region with `MiloJulo isn't in your city yet`, and `in_service_region()` tells the app when the Member's point lies in no active region. Connection Requests and Mode Changes still use Eligible Modes until #104. See docs/adr/0003-member-location.md. (Dating Mode visibility in Discover also replaced by 45; the Eligible Mode change for requests was built in #104, decision 39.)
43. **Requests only to Members in your Discover (#118, 2026-10-16).** `send_request` now also requires the recipient to be inside the sender's Discover Range (null range: anywhere in the sender's Service Region), the same `within_range` rule Discover uses, so a request can't reach a Member the sender could never see. Refused with `that member is not in your Discover`; the app's request sheet shows "This Member is outside your Discover range, so you can't send them a request." Hidden, Paused and Blocked recipients keep the existing `you cannot send a request to this member`. Accepting a request and Mode Changes inside an accepted Connection are not re-checked against range, so moving or narrowing the range never strands an existing request or Connection.

46. **Circle members see each other's photos (#128, founder, 2026-10-16).** Fellow members of a Circle get each other's photo links, as on the Circle's member list: both Visible, no Block, accounts active. Before, a member outside the viewer's Discover Range showed only their initial.
47. **Push notifications (#36, 2026-10-16).** Five events push, all decided in SQL triggers that write `push_queue`: a Connection Request ("New Connection Request" / "<name> wants to connect."), its acceptance ("<name> accepted your request" / "Say hello."), a message (sender's name / "Sent you a message." (never the text, founder 2026-10-16, so nothing private shows on a lock screen), or "Sent a photo", "Sent a video", "Sent a voice note", "Shared an activity"), a Join Request to the host ("New Join Request" / "<name> asks to join <title>.") and its acceptance ("You're going" / "<host> accepted you for <title>."). The first three obey `notify_messages`, Join Requests `notify_activities`; a muted chat sends no message push. Activity Connections, and a pending Connection Request accepted through a join, send only the join push. An insert trigger on the queue calls the `push` Edge Function over `pg_net` (Vault URL and service role key, as the chat-media purge); the function sends through the FCM HTTP v1 API with the service account in `FCM_SERVICE_ACCOUNT`, deletes dead tokens and then the queue row. A push that fails to dispatch stays in the queue (no retry yet). A device token belongs to whichever account last registered it, so a shared phone never gets the previous account's pushes. (A sixth push, the meet nudge, added by 53. Retries added by 57.)
48. **Activities: Post and Joined buttons, host photo, Directions (#134, founder, 2026-10-17).** The full-width Post an activity button becomes two compact buttons, Post and Joined; Joined opens a screen with Going (Activities the Member was accepted into, not yet over) and Waiting (Join Requests not yet answered) tabs, hosted Activities left out, and its badge counts Going (`joined_activities()`). Activity detail gives accepted joiners and the host the venue with a Directions button that opens Google Maps (`Linking`, a `maps/dir/?api=1&destination=` link built from the venue text and Area; no SDK, no API key). The board card keeps only the Area, so the venue stays hidden from everyone else. (Since 20261028090000_board_hides_my_requests.sql, Activities the Member has asked to join, whatever the answer, leave their board; they live on Joined.)
49. **Discover leaves out your Connections (founder, 2026-10-17).** `discover_feed` no longer shows a Member the viewer has a waiting Connection Request with (either direction) or an accepted Connection with; a declined or closed one brings them back. A second request to them was impossible anyway (one active Connection per pair). Profile view, photo links, chat and Inbox are unchanged, so the profile still opens from a chat or a request.
50. **55 Pune Areas, nearest one suggested (#142, founder, 2026-10-17).** The Area catalog grows from 5 to 55 neighbourhoods, each in a zone (West, Pimpri-Chinchwad, Central, East, South), with `lat` and `lng` generated from the centre. The setup Area step asks for location first and suggests the nearest Area if its centre is within about 3 km, computed on the phone from the catalog it already loads (no new SQL, the point is not sent until `set_location` after submit); the list, with a name filter, changes the suggestion and is the fallback when location is refused or too far. A refusal is recorded so `LocationGate` does not ask again. Map view and place search stay deferred (they need a geocoding provider).
51. **One Realtime channel per Member (#145, #144, founder, 2026-10-18).** Live updates go to a private `member:<id>` topic, joined once while the app is signed in, instead of one `connection:<id>` topic per open chat. Database triggers send each event only to the Members it concerns, never back to the one who acted (a Member's own message on a second phone shows on its next catch-up) and never across a Block (`is_blocked` in the trigger). Realtime checks topic access on join and caches it for the connection, so with per-Connection topics a blocked Member kept listening until their JWT refreshed. A broadcast counts one message sent plus one per receiver, so skipping the sender halves the cost. The app catches up on reconnect and on return to the foreground (TanStack `focusManager` follows `AppState`); polls are removed ticket by ticket under #144.
52. **The query cache is kept on the phone (#149, founder approved both packages, 2026-10-18).** `@tanstack/react-query-persist-client` with `@tanstack/query-async-storage-persister` (both JS only, on the existing async-storage) save an allowlist of queries: the catalogs, the Inbox, the board, Joined, my Join Requests, the Circles list and Discover (my state and the feed: other Members' names, ages, Areas and photo ids, never links). Never chat text (the Inbox's last-message text is stripped when saving; the preview fills in on refresh), messages, profiles, Activity detail or signed media links; async-storage is not encrypted. A cold start shows the last data at once, then refreshes. The copy lives 24 h, is dropped when `cacheVersion` in `src/lib/persistCache.ts` changes (bump it when a saved query's shape changes), and is wiped at once on sign-out (so on account deletion too). If the session is found gone on a cold start, the memory is cleared again once the restore finishes, so a slow restore can't bring the last account back.
53. **Meet nudge (#50, 2026-10-18; built overnight, copy and timing for the founder to confirm).** A sixth push: once per Member per chat, a week after a Connection was accepted and both sides have written, "Did you meet <name>?" / "Tell us how it went. It takes a moment." Tapping it opens MeetFeedback. It obeys `notify_messages` and Mute, never crosses a Block, skips Activity Connections (the post-Activity prompt covers them) and stops once the Member answers. A Member with message notifications off, Paused or deleted isn't marked asked, so they are asked once the push would reach them. Sent by a daily pg_cron job at 11:00 India time, so it lands in the day. A pair whose Activity was cancelled has neither prompt.
54. **Account purge erases the whole chat's media (#96, 2026-10-18; built overnight for the founder to confirm).** Deleting the auth user cascades to both sides' messages, so the purge erases from R2 the deleted Member's photos and uploads and all chat media in their Connections, including what the other Member sent; nothing would point at those files afterwards (hard rule 9). Kept: any key a report holds as evidence, without a time limit for now (open: a retention period for report evidence). The order is media, then the record in `completed_erasures`, then the auth user; a failure leaves the erasure queued and the next hourly run starts over safely. Known gap: the other Member can still start an upload into the chat while the purge runs, which could leave one live file; closing it means refusing uploads when either side is deleted.
55. **Report evidence is the original key, not a copy (#96, #97, 2026-10-18; amends decision 17 for the founder to confirm).** Decision 17 and CONTEXT.md say media in a reported message is copied into evidence; nothing copies it: `reports.evidence_media_key` is the photo's or message's own R2 key. The account purge and the Media Expiry purge both skip any key a report holds. A reported chat file past 90 days is marked expired in the chat (Members see 'Media expired') but stays in R2. How long evidence is kept, and whether to copy it to an `evidence/` prefix instead, is open: https://github.com/sadiq1402/milojulo/issues/160.
56. **Admin actions settle reports; profiles are banned, not taken down (#18, 2026-10-18).** `admin_takedown` covers photos, messages and Activities only; removing a Member is `admin_ban`, which needs a reason. Takedown marks the open reports on its target `actioned` and Restore marks them `dismissed`, each with the admin and time; a Ban marks every open report about the Member `actioned` (profile, photos, messages, Activities), so the queue empties as admins act. Dismissed reports no longer count toward Auto-hide, so a Restore isn't undone by the next report; three fresh reporters still hide it again. A banned Member can't file reports. A taken-down message is gone from the table for both sides (admins have it as report evidence). A ban closes the Member's requested and accepted Connections with `closed_by` set to the banned Member (the column references profiles, which an admin may not have), and withdraws Join Requests and cancels Activities only where the Activity hasn't started, so what already happened keeps its history. The audit log is append-only for everyone; the service role can still insert, for later admin Edge Functions. Not built: unbanning; live removal of a taken-down message from an open chat; Join Requests that others sent to a banned host's cancelled Activities stay as they are, as with `cancel_activity`.
57. **Queued pushes are retried for an hour (#167, 2026-10-18).** A pg_cron job, `retry-queued-pushes`, runs every 5 minutes: it hands a push to the push function again when it is still queued and was never handed over (the Vault secrets or pg_net were missing) for a minute, or was handed over more than 5 minutes ago (FCM answered 429 or 5xx), so a push still in pg_net's backlog isn't sent twice. It drops pushes queued an hour ago or more, since a late chat or request push is noise, and any the recipient no longer wants: banned or deleted, that kind of notification turned off, the chat muted (message pushes), or the Connection no longer requested or accepted (closed, declined, blocked). A retry goes to all the recipient's devices, so a Member with two phones can get a duplicate when only one device failed.
58. **Keyboard handling (founder approved the packages, 2026-10-19).** `react-native-keyboard-controller` (with its peer `react-native-reanimated` 4 and Reanimated's required peer `react-native-worklets`) handles the keyboard. With edge-to-edge on (target SDK 36), Android no longer resizes a window for the keyboard, and a React Native `Modal` is its own window, so `adjustResize` did nothing in bottom sheets and React Native's keyboard events never reached them: the send-request note sat under the keyboard. The library reads the keyboard's real height on every device, Modal windows included. `KeyboardProvider` wraps the app; `BottomSheet` adds room for the keyboard under the sheet, which shrinks to fit, and the send-request form scrolls when space is short (small phones, large text). Other screens still use React Native's `KeyboardAvoidingView`; move them to the library's version if one misbehaves.
59. **Chat media limits from a settings row (#182, founder, 2026-10-24; replaces decision 17's video limit).** Chat media limits live in one database row, `chat_media_settings`, that the founder changes with a SQL `update` in the dashboard (docs/runbooks/moderation.md): no deploy, no app release, no admin function and no `admin_actions` entry. Launch values: video up to 15 s, images up to 2 MB, voice notes up to 2 min. The old limits stay as fixed maximums the row can only tighten (video 30 s and 20 MB, image 5 MB, voice 2 min and 5 MB); an empty value means the fixed maximum. No client role reads the row; Members read the limits in force through `chat_media_limits()`. The image limit is checked before an upload link is issued (`start_chat_upload`), video and voice length when the message goes in (`check_message_media`). Refusals are fixed texts without numbers (`image is too large`, `video is too long`, `voice note is too long`, and from the media function `<kind> is too large` and `<kind> must be a <format>`), because the app matches refusals by text; the app adds the numbers from the limits it read. The app checks a video's length before compressing and a photo's size before uploading, stops the voice recorder at the voice limit, and uses the fixed maximums until the server's limits arrive. Media Consent (decision 33) still applies on top.
60. **One media message per Connection per day (#183, founder, 2026-10-24).** In each Connection a Member may send one media message (photo, video or voice note) in any rolling 24 hours; the other side has their own allowance, and so does each of the Member's other Connections. Text is never limited. The number is `chat_media_settings.daily_media_allowance` (launch 1; null switches the rule off), changed by SQL like the other limits (decision 59). Only sent messages count: a taken-down or expired one still does, an abandoned upload does not, and a retried send of the same message id is counted once. It is checked when an upload starts (`start_chat_upload`, so no data is spent on a file that can't be sent) and again when the message goes in (`check_message_media`, under a lock on the sender's `connection_members` row, so two sends at once can't both pass). The refusal is `media limit reached` (the media function answers 429). `chat_media_allowance(connection_id)` gives the caller `remaining` (null: no limit) and `next_at`; when it is used up, tapping attach or holding the mic in the app starts nothing and shows "Next photo, video or voice note in 5 h" on the composer's error line, with no other change to the chat screen. The app reads it on opening the chat, after each media send and on return to the app. Media Consent (decision 33) still applies on top.
61. **Web account deletion: a static page on the MiloJulo domain (#98, founder, 2026-10-25).** The deletion page Google Play requires is one static page on milojulo.co.in (Cloudflare Pages), not part of the later Next.js admin app: the Play listing needs it before launch, and the admin app has no ticket. 62. **Report evidence: kept 90 days at an `evidence/` prefix (#160, founder, 2026-10-25).** When a report is made the media is copied in R2 to an `evidence/` prefix, and the copy is what the report points at; the original then follows its own lifecycle, so the account purge (#96) and the chat media purge (#97) no longer have to skip keys a report holds. Evidence is deleted 90 days after the report, matching chat media (decision 17), unless the report is still open: an open report keeps its evidence for as long as it stays open, which is the only hold there is (`reports.status`; there is no separate hold flag). A scheduled job does the deleting, like the other two purges. Until the copy exists the original is held back: the chat media purge leaves it for a later run and an account erasure waits for the next hourly run, so no file is deleted before its evidence is safe and none is left behind afterwards. Rejected: keeping evidence at the original key (what the code did, and the bug in #160: two owners of one file, so nothing ever deleted it); one year (more retained personal data to declare, no clear safety gain for a beta).
