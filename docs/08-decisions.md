# Decision log

Format: decision, why, alternatives rejected. Update this file whenever a decision changes.

1. **Auth: Supabase Auth with email OTP only (phone later).** Cognito does not come from Supabase and complicates RLS. SMS OTP in India needs DLT registration and costs per message, so it waits for beta funding. Phone attaches to an existing account later.
2. **Backend: Supabase only, with Postgres functions plus a few TypeScript Edge Functions.** One platform, one bill, one deploy tool, free until the beta. Rejected: AWS Lambda with FastAPI (free but needs an AWS account with free-plan expiry rules and extra setup; Python was preferred for build speed); Google Cloud Run (free tier appears limited to US regions, which is far from a Mumbai database); Cloudflare Python Workers (new, 10 ms CPU on free, WebAssembly package limits); Firebase (Cloud Functions and Storage need the pay-as-you-go plan, Firestore is a poor fit for relational, geo and block-aware matching).
3. **Business rules in SQL.** Keeps the language of the thin API layer almost irrelevant, scales with Postgres, and is portable to any Postgres host.
4. **Chat transport: Realtime Broadcast from database triggers** on private channels with RLS on realtime.messages. Postgres Changes was the first sketch but does not scale (single-threaded per-subscriber authorisation).
5. **Media on Cloudflare R2** (founder decision) instead of Supabase Storage: 10 GB free, free egress (video in chat), cheap beyond. Costs: second vendor, payment method may be required, access control must be rebuilt as signed URLs from an Edge Function, delete R2 objects on account deletion. Store object key plus provider so it can move.
6. **Matching: rule-based SQL, no LLM in V1.** Cuts cost and complexity; AI becomes one more signal later.
7. **Moderation: invite-only plus manual approval of profiles and photos** for the first few hundred users. *Superseded by 15.*
8. **Android first** (Google Play closed test doubles as the beta); iOS after the Apple fee is paid.
9. **Scope expansion (founder decision):** Dating, Serious, Casual, Networking, Circles and media in chat were added to V1. Risk flagged: timeline is now a floor; Casual and media raise moderation and store-review exposure; build each mode behind a switch and open in stages if time is short.
10. **Colour: Orchid pop** (founder decision after research on women's colour preferences and competitor palettes). First scheme (rosewood and ochre on beige) was dropped for looking institutional.
11. **Logo: not final.** Overlapping-circles mark rejected (Mastercard resemblance). Leading candidate Mingle plus Tail wordmark; trademark search pending.
12. **UI standards:** 48 hit targets, 4-pt grid, pill controls, soft-shadow cards (see docs/05-ui-standards.md).
13. **Business idea:** the founder chose to focus on MiloJulo only. Revenue is postponed until retention is proven; likelier paths are ticketed events and venue partnerships before premium subscriptions.
14. **Mobile: React Native CLI (bare workflow), no Expo** (founder decision; the assistant had recommended Expo with development builds).
    - Why: full control of the native projects (Gradle/Xcode), no dependence on Expo's tooling or build service, free local Android builds.
    - Accepted costs: hand-maintained native config and React Native upgrades (use the Upgrade Helper), manual autolinking and native-module setup, FCM set up directly (no Expo push API), iOS builds require macOS (a Mac or macOS CI) because local iOS builds are impossible on Linux, no built-in over-the-air updates.
    - Bootstrap: `npx @react-native-community/cli@latest init` (the old `npx react-native init` is deprecated; projects must declare `@react-native-community/cli` as an explicit devDependency).
    - Escape hatch if it becomes painful: `npx install-expo-modules@latest` adds Expo modules to a bare app without a rewrite.
    - Consequences for other decisions: push is FCM only; Android-first beta (decision 8) fits because iOS needs a Mac or CI.
15. **No pre-approval of profiles or photos (founder decision, 2026-10-07; supersedes 7).** Members go live on profile submission; moderation is after the fact via reports (24-hour target), bans, word filter and invite codes (removed by 27). Accepted risk: nothing screens photos before others see them, which weakens the store-review answer for UGC with Casual mode; automated photo screening is the fallback. See docs/adr/0002-no-pre-approval-of-profiles-or-photos.md.
16. **Connections carry a Mode and are per-pair history rows** (one active per pair, consent-based Mode Change, accepted Join Requests create an Activity Connection). See docs/adr/0001-connections-are-per-pair-history-with-a-mode.md.
17. **Chat media limits and retention (2026-10-07).** Report-only moderation; video up to 30 s and 20 MB, voice notes up to 2 min; chat media deleted from R2 90 days after sending (message stays, shows "media expired"); media in reported messages copied to evidence and kept for the safety-retention period set by the lawyer. Casual Connections require Media Consent from both sides before images or video.
18. **First name is part of the profile minimum (2026-10-09).** A profile cannot be submitted, or later edited, without a first name, alongside the photos, prompts, Mode and Area; submission also requires the age gate and consents to have been passed. Photo upload confirmation is service-role only, because only the upload Edge Function can check that the object exists in R2.
19. **Chat history after a Block, ban or Auto-hide (founder decision, 2026-10-12).** A Block closes the pair's Connection, and the closed Connection stays in both Members' history with the same details as an ordinary close, so the blocked Member can't tell they were blocked. Photo links for a blocked pair are still refused by the media-links function (#35, hard rule 9). A banned or Auto-hidden Member stays in other Members' history by first name, but without a cover photo until an admin restores them.
20. **Chat UI values (2026-10-12).** docs/05 already set the bubble (radius 22, 6 on the tail corner, 16/22 text) and the composer; tokens now carry them, plus composer padding 10 12 (from the Chat mockup) and a 10 orchid unread dot (from the Chats mockup). The first-meet safety note sits at the start of every chat's history rather than only in new chats, so in practice it's seen when a chat is new or short.
21. **Inbox badge and Mode-coloured chips (2026-10-13).** The Inbox tab shows a count of Connection Requests waiting for the Member, as an orchid pill badge on the tab icon (docs/05 "Tab badge", token `sizes.tabBadge`); requests aren't broadcast, so the count refreshes every 30 s. Chips can carry a Mode tint (`Chip tint`), as in the Discover and Send Request mockups, keeping Mode colours to tags and chips (docs/06).
22. **Discover and profile view details (2026-10-13).** The profile's second prompt card uses `lilacSoft` (#E3D4FF), the mockup's colour, which is also the Casual tint; it's a card background, not a Mode marker. The profile uses the standard top bar (back, menu) instead of the mockup's back button floating over the photo, keeping 48 targets clear of photo content. Until signed photo URLs exist (#35), feed cards and the profile hero show a photo-tone placeholder with the initial.
23. **Activity Board visibility and edges (2026-10-13).** The board hides Activities whose host is Auto-hidden (after Reports), banned or deleted; a Paused host's Activities stay, since pausing only hides you from Discover. Deleting an Activity (for example with its host's account) deletes Activity-card messages that point at it rather than leaving broken cards. Until the expiry job runs (every 15 min) the host can still edit or cancel an Activity whose time has passed; the board already hides it. Once an end time is set it can be changed but not cleared. The Locked Activity rules arrive with Join Requests (#14), the first way an Activity can lock.
24. **Activity Board screens (2026-10-13).**
    - The board is one list with Tonight, This weekend and Later headings rather than the mockup's segmented control, so nothing is hidden behind an empty tab.
    - Cards are tinted by Activity type (`activityTones`: the photo tones plus the Networking tint), as in the mockup; the type shows as a plain tag, not a Mode colour.
    - Date and time without a date-picker dependency: day chips (Today, Tomorrow, then the next five weekdays), a start-time Stepper in 30-minute steps and a length Stepper (30 minutes to 12 hours, or no set end). Everything is in India time whatever the phone's zone. The Stepper is a new shared component (docs/05).
    - Editing can't change the type (`update_activity` has no type) or remove a set end (null keeps it). A Locked Activity's form shows only the details and Spots (which can only go up), with a note saying why.
25. **Join Requests (2026-10-13).** One Join Request per Member per Activity: once declined, cancelled or withdrawn it can't be asked again. Accepting a Join Request when the pair already has a waiting Connection Request accepts that request as it stands (its Mode and note), rather than making a second Connection; an existing accepted Connection is reused with its Mode. A Block cancels waiting and withdraws accepted Join Requests between the pair, either way round. Joining, answering and withdrawing all stop once the Activity has started, and the host can't answer a banned, deleted or Auto-hidden requester (the same Members the host's list leaves out). An accepted joiner keeps reading the Activity and its venue until it ends, even while Paused or after an Auto-hide. Activity Connections don't count towards the Request Cap, since nobody sent them.
26. **Join Request screens (2026-10-13).**
    - Accepting a Join Request from the Inbox opens the chat with the joiner, as accepting a Connection Request does; accepting on the Activity itself keeps the host there (several may be waiting) and moves the joiner to a Going list with Open chat.
    - Cancel request and Withdraw both ask first and say the Member can't ask to join that Activity again (one Join Request per Member per Activity); a declined, cancelled or withdrawn request leaves a short note instead of the button.
    - "Ask to join" (the mockup says "Request to join"), so the button doesn't read like a Connection Request. A full Activity shows "No spots left" instead of the button.
    - The phone's clock decides only what to offer once an Activity has started or isn't open (no Ask to join, Cancel or Withdraw for the joiner, no Accept or Decline for the host); the database enforces the start itself. A request still waiting at the start says the host didn't answer it in time, and an accepted joiner whose chat was closed is told so instead of seeing Open chat.
    - Incoming Join Requests sit with Connection Requests under "Waiting for you" and count towards the Inbox badge; the caller's own waiting ones are listed under "Sent" and open their Activity. Join Requests aren't broadcast, so the list and badge poll every 30 s, like Connection Requests (decision 21).
27. **Open sign-up, invite codes removed (founder decision, 2026-10-13).** Anyone who signs in with an email can become a Member: the 18+ age gate and consents are the way in, and `accept_consents()` creates the profile row. `check_invite`, `redeem_invite`, `invite_codes` and `invite_redemptions` are dropped, and the app's flow is Welcome, Email, code, Date of birth and consents, profile setup. Why: lower friction for the beta. Accepted costs: no trust layer and no cluster control from codes (offline events and outreach now do that), and bot protection depends on Cloudflare Turnstile (#70) and a disposable-email blocklist (#71), neither built yet. The Reviewer Account still exists for store review, seeded with its date of birth and consents. Supersedes the invite-code parts of docs/01 and decision 15.
28. **Profile photo links (#35, 2026-10-14).** Pending uploads live in their own table (`photo_uploads`), not as unconfirmed `photos` rows, so a replacement can upload while the old photo at that position stays live, and an unconfirmed upload is never anyone's photo. Confirming inserts the new photo before deleting the old one, so replacing a photo of a Submitted Profile with only 2 never trips the minimum; the replaced file is deleted from R2. One slot per position (a new one replaces the earlier); slots older than an hour can't be confirmed and are discarded (with their files) when the Member's next slot is made. Who may get a photo link: the owner (confirmed, not taken down; hidden included); anyone else only live photos of a Member who is not banned, deleted or Auto-hidden, with no Block either way, and whom they may see in Discover or the profile view, or who shares with them a Connection (any status but declined: a waiting Connection Request counts both ways, so each side sees who is asking or being asked, and closed history keeps its faces), a waiting or accepted Join Request, or a place among the same Activity's accepted joiners ("shares an Activity" read as fellow joiners; host and joiner are covered by the Join Request). Join Request access persists after the Activity is cancelled or over, as history, like a closed Connection. Upload links point at a staging key (`uploads/<member id>/<photo id>.jpg`) with Content-Type and Content-Length signed; on confirm the function checks the staged file, copies it server side to the live key and deletes the staged one, so an upload link that is still valid can never overwrite a live photo. Unconfirmed staged files are removed by an R2 lifecycle rule on `uploads/` (1 day), set by the founder. A photo an admin took down keeps its file when the Member replaces or deletes it (evidence). Members delete photos through the function's `photo-delete` (`delete_photo()`, which keeps the profile minimum) so the file goes too; direct deletes under RLS remain for now and leave the file. A banned or deleted viewer gets only their own photos. Extra refusals beyond the contract: `accept the terms first` (no profile yet), `your account cannot add photos` (banned or deleted), `choose a photo position from 1 to 4`, `no photo to delete` (404), `add at least 2 photos` (400, from the minimum), `ask for at most 60 photos at a time`, `photoIds must be a list of photo ids`, `send a JSON body`, `unknown action`, `use POST`. A presigned URL necessarily carries the object path, so the key (`<member id>/<photo id>.jpg`, both already known to the app) is visible inside the link; it is useless without the signature. Signing is hand-rolled SigV4 with Web Crypto, tested against AWS's published examples; the function runs with `verify_jwt = false` and checks the caller itself so a signed-out request gets `sign in first` (such calls still cost an invocation).
29. **Profile setup screens (2026-10-14).**
    - Five steps in the mockups' order (Basics, Photos, Prompts, Modes, Interests); each step saves when the Member leaves it, by Next or by Back (the top bar's or Android's), so nothing typed is lost; Back saves without the step's minimum (blank prompt answers are left out, since an empty prompt would count toward the minimum) and a failed save keeps the Member on the step with the reason. Photos save as they upload. A returning Member resumes at the first step whose minimum isn't met. Interests and availability are optional, so the last step is always reachable. Step 1 has no Back (consents are done) and offers Sign out instead.
    - A refusal from `submit_profile()` opens the step that fixes it with the reason on that step, until the Member changes something there; success goes straight to Discover.
    - Photos: four 4:5 slots, the first is the main photo; only photos neither hidden nor taken down fill a slot, as in the profile minimum. Tapping a photo offers Make main photo, Move earlier, Move later, Replace and Remove; moving swaps with the photo there in one `move_photo` call, and removing closes the gap so the next photo becomes the main one. While a photo uploads, the other photos can't be moved or removed and the step can't be left (Android's back says to wait). Upload progress is a spinner, since the upload is a plain `fetch` PUT; a failed upload keeps Retry and Cancel on its slot and its reason above Next, which fits at 130% text. The mockup's "a person reviews every photo" note is replaced by a tip about the main photo (decision 15).
    - Prompts use the catalog's first two active questions (only two exist); with fewer than two the step says prompts aren't available instead of saving. A question picker waits for a longer catalog.
    - Modes are option cards; Casual carries an "18+ · adults only" tag. Choosing a Dating Mode shows own gender, genders to meet, an age range starting at the Member's age ±5 (18 to 99) and a maximum distance starting at 15 km (5 to 50 in steps of 5); these defaults are saved only while a Dating Mode is held. Networking shows optional profession, Industry and Career Stage.
30. **Circles (#15, 2026-10-14).** Circles are admin-created only: `admin_create_circle`, `admin_edit_circle` and `admin_archive_circle` are guarded by `is_admin()` and are not called by the app (seed and dashboard only). Members reach Circles through `browse_circles()` (active Circles for a visible Member, joined first then by name, each row carrying `member_count` and `i_am_member`), `get_circle()` (one Circle: active ones for a visible Member, plus the caller's own Circles and admins, so a member or admin still sees an archived Circle), `circle_members_of()` (fellow members only to a member of that Circle, excluding the caller, the non-visible and either-way blocks), `circle_activities()` (a Circle's upcoming Activities for a visible caller) and `join_circle()` / `leave_circle()`. Neither `circles` nor `circle_members` is readable or writable directly. Joining is idempotent and needs a visible profile and an active Circle (`your profile is not visible`, `no circle to join`); leaving refuses when the caller is not a member (`you are not in this circle`) and leaves the Member's posted Activities untouched. `post_activity` gained a trailing `circle_id`: posting to a Circle requires membership of that active Circle (`join the circle to post to it`). `activity_board()` and `get_activity()` gained `circle_id` and `circle_name`; `circle_name` (and `circle_activities`'/the board's label) is NULL once the Circle is archived (`is_active = false`), so an archived Circle drops its label while its Activities stay. A paused fellow member is treated as non-visible and so is left out of the member list, matching the contract's "excludes non-visible". `created_by` on `circles` has no foreign key, so an admin without a profile row can still create one.
