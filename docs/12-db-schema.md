# V1 database schema

Concrete V1 schema built from docs/03-data-model-rls.md and docs/11-screen-data-map.md, revised after the 2026-10-07 design session (glossary in CONTEXT.md, decisions 15 to 17, docs/adr/). V1 only: no columns for deferred features. Where this differs from docs/03 or docs/11, this file wins.

33 tables in `public`, plus a policy on `realtime.messages`. Every table has RLS enabled, default deny.

## Conventions
- Primary keys: `uuid default gen_random_uuid()`, except user-keyed tables (`profiles.id = auth.users.id`) and messages (client-generated id).
- User references point at `profiles(id)`; `profiles.id` references `auth.users(id) on delete cascade`, so deleting the auth user removes everything the user owns, including both sides of their Connections and messages. Admin columns point at `auth.users` instead (`photos.removed_by`, `reports.handled_by`, on delete set null); `admin_actions.admin_id`, `circles.created_by` and `completed_erasures.member_id` have no foreign key.
- Times are `timestamptz`. Most tables have `created_at default now()` (not `banned_terms`, `service_regions`, `member_locations`, `device_tokens`, `meet_nudges`, `completed_erasures`).
- Fixed lists are Postgres enums (adding a value later is one `alter type`). Lists admins edit are catalog tables.
- Admin = `auth.jwt() -> 'app_metadata' ->> 'role' = 'admin'`, set only with the service role. Wrapped in `is_admin()`. No admin table.
- Owners edit only safe columns: `grant update (col, ...)` to `authenticated`, never table-wide update. Status and moderation columns change only through functions or admin.
- No pre-approval (decision 15): content is live when written; moderation is after the fact through `hidden_at` (Auto-hide) and `removed_at` / `banned` (Takedown).

Connection rules (docs/adr/0001):
- One Requested or Accepted Connection per pair; older rows stay as history.
- `send_request()`: mode must be an Eligible Mode from sender to recipient (one the recipient chose that the sender may see in Discover, decision 39); accepting keeps that Mode on the Connection; sender and recipient both visible (so neither paused); recipient inside the sender's Discover Range (null range: the sender's Service Region), else `that member is not in your Discover` (decision 43; accepting and Mode Changes are not re-checked); Request Cap of 10 per rolling 24 h; no re-request by the same sender within 30 days of a decline; never while a Block stands.
- Mode Change: one open proposal per Connection; `to_mode` must be an Eligible Mode from the proposer to the other side, checked again when they accept; an open proposal older than 7 days counts as lapsed; a declined proposer cannot propose again for 7 days. Accepting updates `connections.mode`.
- Dropping a Mode from a profile leaves existing Connections and their Mode untouched.

Realtime: an insert trigger on `messages` broadcasts the row to the other Member's private topic `member:<id>` (not the sender's, never across a Block); a policy on `realtime.messages` lets a Member join only their own topic (decision 51). Changes to `last_read_at` (`read`), `media_consent` (`media-consent`) and Mode Change proposals or answers (`mode-change`) send `{connection_id}` to the other Member the same way (`send_to_other_members`: not the actor, not across a Block); the app refetches that Connection's query. Connection Requests (sent, answered, closed) send `connection` and Join Requests (sent, answered, withdrawn) send `join-request` to whichever of the two did not act (`send_to_pair`, nothing across a Block); the app refetches the Inbox or the Activity lists. Unread = messages newer than my `last_read_at`. Mute only suppresses push for that Member.

Chat media: the media function caps uploads at the fixed maximums (image 5 MB, video 20 MB, voice 5 MB); the settings row tightens the image size and the video and voice lengths (decision 59). Media Expiry: the `purge-chat-media` Edge Function (#97; `expired_chat_media(batch)` and `mark_chat_media_deleted(ids)`, service role only; a file whose report evidence is still being copied waits for a later run, #160), scheduled daily at 03:00 India time by the pg_cron job `purge-chat-media` through pg_net (URL and key from Vault, supabase/README.md), deletes R2 objects older than 90 days and sets `media_deleted_at`; the message stays.

Moderation:
- **Auto-hide**: `report()` sets `hidden_at` on the target profile, photo or Activity once 3 distinct reporters (word-filter flags excluded) have reported it within 7 days. An admin then clears `hidden_at` or takes it down.
- **Takedown** (`admin_takedown`): photo `removed_at` and `removed_by`, message `removed_at` (Members no longer read it), Activity `status = removed`. A profile is not taken down (`ban the member instead`): the Member is banned (`admin_ban`, `status = banned`, `banned_at`, `banned_reason`; a reason is required). **Restore** (`admin_restore`) clears `hidden_at` on a profile, photo or Activity; it does not undo a Takedown. Takedown marks the open reports on its target `actioned`, Ban every open report about the Member, Restore marks the target's open reports `dismissed`; dismissed reports don't count toward Auto-hide (decision 56). Every one writes `admin_actions`.
- **Ban**: closes all the Member's requested and accepted Connections (chats read-only for the other side), withdraws or cancels their Join Requests and cancels their open Activities that have not started yet (past ones keep their history), removes their Circle memberships.
- **Word filter** (triggers on display names, prompt answers, Activity titles and descriptions, messages): a term matches case-insensitively as a whole word (a multi-word term as a phrase; letters, digits, underscore and all of Devanagari U+0900 to U+097F count as word characters, so a matra or virama is never a boundary), via `matches_banned_term(text)`, which builds one combined pattern from all terms per call (security definer, not executable by app roles). Profile text and Activities that match are refused with `that wording isn't allowed; please change it` on insert or update; messages are delivered unchanged and filed as a `word_filter` report (`reporter_id` null, `target_user_id` the sender, evidence from `message_evidence(message)`, the snapshot `report()` also uses), which never counts toward Auto-hide.
- **Reported media** (#160, decision 62): a report is stored with `evidence_media_key` pointing at a copy under `evidence/<report id><ext>` and `evidence_source_key` holding the live key it is taken from; a `before insert` trigger (`set_report_evidence_key()`) does this, so `report()`, the word filter and admin takedown are unchanged. The `copy-evidence` Edge Function makes the copy: `pending_evidence_copies(batch, skip)` and `mark_evidence_copied(ids)` (service role only), called at once by an `after insert` trigger through `dispatch_evidence_copies()` and again by the `copy-report-evidence` pg_cron job every 15 minutes for anything left over; a source that is already gone is marked rather than retried for ever. Until the copy exists both purges keep the original (`evidence_pending_for(key)`, used by `erasure_media_keys` and `expired_chat_media`); once it exists, the original follows its own lifecycle. Evidence copies are kept 90 days from the report (cleanup not built yet, #160).
- Admin queue: open reports (24 h target), Auto-hidden items, and a recently-joined list for spot checks (no approval). No queue functions or admin page yet: the founder works from the Supabase dashboard and calls the admin functions there.

Learning loop (Kept Connection = both rows have `did_meet` and `keep` true):
- Activity: from 2 h to 14 days after it ends, `pending_meetup_feedback()` lists the host and each accepted, non-withdrawn joiner to each other (joiners are not asked about other joiners); the app shows them as prompts on the Activities tab. No push for these.
- Connection: a "We met" action in chat, plus one push nudge (`send_meet_nudges()`) 7 days after acceptance if both Members have sent messages.

## Functions
Every function has a fixed `search_path`. Unless a row says otherwise, business functions are security definer and executable by `authenticated` only; internal helpers are executable by the service role only.

Shared helpers:
- `is_admin()` (invoker; callable by every role, used in policies), `is_blocked(a, b)` (definer, internal), `is_visible(member)` (invoker, internal: active, submitted, not paused, not hidden, not deleted, no current consent document missing or withdrawn (`consent_withdrawn`), at least 2 live photos), `is_reachable(member)` (invoker, internal: not banned, deleted or Auto-hidden, no consent withdrawn), `eligible_modes(a, b)` (invoker, internal: shared Modes, Dating Modes filtered by both Members' Dating Preferences).
- Used by policies, so executable by `authenticated`: `can_send_in(connection)` (messages insert; the caller's `member_can_send_in`), `hosts_activity(activity)` (activity_requests select).
- The chat media send rule (#186), internal: `member_can_send_in(member, connection)` (an Active side of an accepted Connection, no Block either way, no current consent withdrawn) and `check_media_send(member, connection, kind, size, duration_ms)`, which raises the Member's refusal unless they may send that media now: `no connection`, `media is off in this chat` (decision 33), `image is too large`, `video is too long`, `voice note is too long` (decision 59), `media limit reached` (decision 60, after locking the sender's `connection_members` row). `start_chat_upload` (with the size) and `check_message_media` (with the duration) both call it.
